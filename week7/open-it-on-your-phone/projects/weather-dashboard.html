The problem

A weather dashboard is easy to build as one large API handler, but that approach mixes external API calls, validation, persistence and UI concerns. This project was used to practise a maintainable full-stack structure while making repeated forecast requests measurably faster.

My role

I built the FastAPI backend, React and TypeScript interface, WeatherAPI integration, persistence workflow, Redis caching and test coverage. I also measured repeated-request latency locally to verify that the cache changed observable performance rather than merely existing in the code.

How it works

The React client sends search or geolocation requests to validated FastAPI routes. A weather service checks Redis using normalised cache keys before calling WeatherAPI. A separate record service handles persisted weather records through repository and database layers using SQLAlchemy and SQLite.

Technical decisions

The backend separates routes, services, repositories and database models to keep HTTP handling away from business and persistence logic. Cache entries use configurable TTLs. Fail-open behaviour means a cache problem should not prevent a live weather request from succeeding. Browser geolocation is optional rather than required.

Testing and evaluation

Pytest covers API validation, service behaviour, repositories and error cases. The cache benchmark used 20 repeated local requests. Average repeated-request latency fell from 219 ms to 23 ms after caching, an 89.5% reduction and approximately 9.5× speed-up.

Outcome

The project delivers live conditions, five-day forecasts, browser geolocation and persisted weather records through a responsive interface. More importantly, it demonstrates how an external-data application can be organised into testable layers and evaluated with a concrete performance measurement.

Limitations and next steps

The benchmark is local and does not represent production traffic or geographically distributed users. SQLite is suitable for the project but not the intended final database for high concurrency. Future work could add observability, rate-limit handling and deployment-level load tests.
