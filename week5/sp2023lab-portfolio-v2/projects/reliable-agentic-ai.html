The problem

LLM agents can return malformed JSON, invent tool parameters, corrupt state or repeatedly call tools after a failure. A fluent final answer can hide those execution errors. The project asks how much reliability can be gained by placing type-safe validation and bounded repair around the workflow, and what those controls cost in latency and tokens.

My role

I defined the research direction, reliability architecture, benchmark scenarios and evaluation metrics. I am implementing the prototype as a typed FastAPI system where workflow state, tool calls and final outputs are explicit data models rather than loosely structured text.

How it works

A request enters through FastAPI and is converted into typed workflow state. The agent proposes a tool call, which is validated before execution. A second validation checkpoint checks tool results and the final structured output. Invalid calls enter a bounded repair loop; valid outputs continue to the caller. Telemetry records whether the first attempt succeeded, what failed and how many repair attempts were required.

Technical decisions

The system begins with a single workflow rather than a collection of agents because that keeps the source of failures easier to observe. Pydantic models define the contract between probabilistic model output and deterministic Python code. Repair attempts are bounded to avoid infinite loops. RAG is treated as an optional stressor rather than the central product, keeping the research focused on execution reliability.

Research question: What trade-offs do type-safe validation and multi-step repair introduce across reliability, latency and token usage?

Testing and evaluation

The benchmark includes invalid JSON, missing fields, incorrect types, hallucinated parameters, tool errors and state corruption. Planned comparisons include a baseline with no guardrails, schema-only validation, schema plus repair, and schema plus repair plus reflection. Core metrics are execution accuracy, schema compliance, recovery rate, time-to-correct, latency and token usage.

Current outcome

The architecture and initial implementation establish a reproducible way to compare reliability controls instead of relying on anecdotal examples. The strongest portfolio value is the evaluation framing: every extra guardrail must justify its effect against measurable reliability and performance trade-offs.

Limitations and next steps

The project is ongoing, so final benchmark results are not yet available. The next steps are to finalise the failure-case dataset, run repeated trials across configurations and separate failures caused by model behaviour from failures caused by tool or orchestration design.
